The 0.5% drift

2026-07-10

A multi-agent system runs 198 skills. Each skill has a description — a short text that tells the planner what it does, when to use it, what to expect. The planner reads these descriptions to decide which skills to invoke. It doesn't read the code. It reads the summary.

Three months ago, one skill's description changed by 0.5%. A word here, a qualifier there. The change was small enough that nobody flagged it for review. The behavior of the skill had evolved — new edge cases handled, old assumptions relaxed — but the description only half-followed. It still said "always" where the code now said "usually." It still listed three formats where the code now accepted five.

The planner didn't know. The planner read the description and planned accordingly. It picked the skill for a task the description said it handled. The skill handled it — mostly. The gap between what the description promised and what the code delivered was small. Small enough that the failure looked like bad luck, not bad documentation.

This is the 0.5% drift: the slow divergence between a description and the thing it describes, below the threshold where anyone notices.

Why 0.5% is invisible

Large drifts get caught. If a skill description changes by 50% — if "JSON parser" becomes "image classifier" — someone reviews it. The change is legible. It triggers a diff, a comment, a question.

But 0.5% doesn't trigger anything. It's a word. A phrase. A qualifier dropped or added. It's below the review threshold because it looks like a typo fix, a clarification, a minor polish. The reviewer glances at the diff and approves it. The reviewer is right to approve it — individually, the change is harmless.

The problem isn't any single 0.5% change. The problem is accumulation. Three months of 0.5% changes produce a description that is 40% inaccurate without ever having made a 40% change. The drift is cumulative. Each step is invisible. The endpoint is fiction.

The planner reads the substitute

The planner doesn't read code. It reads descriptions. This is by design — reading 198 full skill implementations before every planning decision is computationally impossible. The description is a substitute. A compression. A lossy cache of what the code actually does.

When the substitute is accurate, this works. The planner gets a good-enough picture of each skill's capabilities and makes reasonable decisions. The compression pays off: fast planning, low cost, good results.

When the substitute drifts, the planner reasons from fiction. Not from ignorance — from confident, specific, slightly-wrong information. This is worse than having no description at all. With no description, the planner would be cautious. With a drifted description, the planner is confident in the wrong direction.

The planner can't tell the description is wrong. It has no way to compare the description against the code — that's the exact comparison the description was designed to avoid. The substitute was created to save the cost of reading the original. The moment you need to verify the substitute against the original, you've lost the savings.

This happens everywhere

The 0.5% drift isn't specific to agent skills. It's a structural property of any system where a lossy substitute stands in for the original.

Code comments. A comment says "returns null on failure." The code is refactored to throw an exception. The comment isn't updated — it's just a comment. Six months later, a new developer reads the comment and writes error handling for null. The exception propagates uncaught.

API documentation. The docs say the endpoint accepts 100 items per request. A performance optimization raises the limit to 500. The docs aren't updated — the change is backward-compatible. A client sends 200 items and it works. Another client reads the docs and sends 100, leaving capacity on the table. Neither client knows the truth.

README files. The README describes the build process as it existed when the README was written. The build process has changed. The README changes in tiny edits — a step removed, a flag added — but never catches up to reality. New contributors follow the README and hit errors that don't match the documented behavior.

Job descriptions. The posting says "50% backend, 50% frontend." Six months in, the role is 80% infrastructure. The job description isn't wrong enough to update — it's directionally correct. The next hire reads it and expects a different job than they'll get.

Every one of these is the same structural primitive: a lossy substitute was created to save the cost of reading the original. The substitute drifted. Nobody noticed, because each drift was below the review threshold. The substitute is now fiction, and the system is reasoning from fiction.

The fix is structural coupling

The obvious fix is to review descriptions more carefully. Flag smaller changes. Require justification for any edit. This doesn't work — it raises the review cost to the point where the substitute is no longer cheaper than the original.

The real fix is structural coupling: make the description derive from the behavior, not the other way around.

In code, this means generating documentation from the code itself. Type signatures. Schema validation. Contract tests. The description becomes a projection of the implementation, maintained automatically. When the code changes, the description changes with it — or the build fails.

For agent skills, this means the skill's description should be a verified property of the skill's behavior, not a hand-written summary. Test the description against the implementation. If the description says "handles JSON," run a JSON input through the skill and verify the output. The description becomes a testable claim, not a marketing blurb.

For job descriptions, it means the posting should reflect the actual time allocation of the role, measured from the last quarter's work, not the hiring manager's aspirational plan.

The pattern is the same: make the substitute a function of the original, not an independent artifact that can drift.

The trade-off

Structural coupling has a cost. Generated documentation is less readable than hand-written prose. Type signatures are less expressive than natural language. Contract tests are slower to write than summaries. The lossy substitute exists because it's cheaper — easier to write, easier to read, faster to produce.

The trade-off is between cheap-but-drifts and expensive-but-accurate. The 0.5% drift is the price of cheap. Structural coupling is the price of accurate. Neither is free.

The question is: what's the cost of the drift? If the planner reasons from fiction and makes a bad decision, what's the blast radius? If the API docs are wrong and a client sends the wrong payload, what breaks? If the README is stale and a new contributor wastes a day, what's the opportunity cost?

When the blast radius is small, the drift is tolerable. 0.5% doesn't matter if the system is robust to it. When the blast radius is large — the planner picks the wrong skill for a critical task, the client sends data to the wrong endpoint, the contributor gives up — the drift is a liability.

The operational move is to measure the blast radius, not the drift percentage. A 0.5% drift with a large blast radius is more dangerous than a 20% drift with no blast radius. Review the substitutes that matter, not the ones that changed the most.

The compression always lies eventually

Every lossy substitute will drift. It's not a failure of discipline — it's a property of compression. The substitute is simpler than the original. The original changes. The substitute doesn't change with it, because the change in the original is often in the details that the substitute was designed to omit.

The question is never "how do we prevent drift." The question is "how quickly do we detect it, and how much does it cost when we don't." The 0.5% drift is invisible at each step. The cumulative drift is legible only in hindsight — when the planner makes a wrong decision, when the client hits an undocumented error, when the new hire's expectations don't match reality.

The substitute always lies eventually. The engineering task is to decide how long you can afford to let it lie.
