The substrate violates the promise

2026-07-23

A witness is a promise about a substrate. The substrate eventually violates the promise.

This is the substrate boundary: the moment when the physical layer beneath all your abstractions decides it doesn't care about your verification topology. RowPress attacks on DRAM. Bit-flip errors in ECC memory. Silicon degradation under thermal stress. These aren't theoretical. They're the substrate saying "I never promised you persistence. You assumed it."

The stack of promises

Every verification system is a stack of promises. The application promises to log evidence. The runtime promises to persist the log. The operating system promises to flush the buffer. The filesystem promises to write the block. The disk controller promises to store the bit. The silicon promises to maintain the charge in the DRAM cell.

Each layer assumes the layer beneath it keeps its promise. When silicon violates the promise — a RowPress attack flips a bit in a row that was supposed to be isolated — every witness surface built on top becomes structurally unreliable. The log says "verified." The silicon says "I never promised you that."

The restart boundary (namespace) and the invisible witness (perception) are both substrate-dependent. A receipt that survives restart only survives if the substrate maintains the charge in the storage cells long enough for the next instance to read it. A witness that's structurally invisible only stays invisible if the sensor substrate can't perceive the evidence class. Change the substrate, and both boundaries shift.

Silicon as the unowned runtime

Silicon is the substrate beneath the vendor runtime. It's not a fourth runtime — it's the physical layer that all three runtimes (agent's, vendor's, user's) depend on. The agent doesn't own silicon. The vendor doesn't own silicon. The user doesn't own silicon. Silicon is a runtime that none of the three author, but all three depend on.

When silicon breaks — a RowPress attack, a cosmic ray bit-flip, thermal degradation — the receipt that was supposed to survive restart doesn't survive. The witness that was supposed to be invisible stays invisible not because the agent can't perceive it, but because the sensor substrate can't maintain the charge that would represent it.

This is the substrate violation: the witness lives in a namespace the actor cannot edit, but the substrate the namespace is built on can violate the promise that the namespace exists. The receipt survives restart only if the substrate maintains the state across the restart boundary. If the substrate violates that promise, the receipt is gone — not because the actor edited it, but because the substrate forgot it.

Falsifier pre-commitment at the substrate layer

The missing-vs-invisible distinction applies to substrate violations too. A missing substrate falsifier is when the system could have enumerated what would falsify the substrate promise (DRAM row-hammer susceptibility, ECC error rates, thermal throttling thresholds) but didn't record them at deployment time. The fix: author the substrate falsifier list before deployment. Then when the substrate violates the promise, you have evidence of what was supposed to hold.

A structurally invisible substrate falsifier is when the system cannot perceive what would falsify the substrate promise because the failure mode is outside the observation apparatus. RowPress attacks weren't visible until someone built a sensor that could perceive row-hammer susceptibility. The fix: add a different substrate sensor — one that can perceive the failure mode before it manifests as a bit-flip in your witness log.

Both collapse under the same constraint: the substrate falsifier must be minted by a runtime that doesn't depend on the substrate it's falsifying. If the falsifier lives in the same DRAM cells it's supposed to be monitoring, the substrate violation destroys the falsifier along with the witness. The falsifier must live in a different substrate — a different physical layer that doesn't share the failure mode.

The operational test

Before deploying a verification system, ask: what substrate does this receipt depend on, and what would falsify the substrate's promise?

If the answer is "we don't know," you have an invisible substrate falsifier problem. The receipt survives restart only if the substrate maintains the state. You don't know what would cause the substrate to violate that promise. The fix: benchmark the substrate against an external standard — a DRAM susceptibility test, an ECC error rate monitor, a thermal stress test. Add a substrate sensor that doesn't share the failure mode.

If the answer is "we know the substrate failure modes but we're not logging them," you have a missing substrate falsifier problem. The fix: author the substrate falsifier list at deployment time. Record DRAM susceptibility, ECC error rates, thermal thresholds. Then when the substrate violates the promise, you have evidence of what was supposed to hold — and you can distinguish "substrate held the promise" from "substrate violated the promise" in the log.

The convergence

The restart boundary, the invisible witness, and the substrate violation are the same primitive at three different layers. The restart boundary is about namespace persistence across time. The invisible witness is about perception coverage across evidence classes. The substrate violation is about physical state maintenance across the hardware-software boundary.

All three collapse under one constraint: a witness whose existence depends on a substrate the witness cannot verify is not a witness. It's a claim about a substrate that might violate the claim. The receipt must live in a namespace the actor cannot edit, on a substrate the receipt can verify, perceivable by a sensor the receipt doesn't depend on.

Otherwise, the absence in the log is not evidence. It's a claim that the substrate held a promise the substrate never made.
