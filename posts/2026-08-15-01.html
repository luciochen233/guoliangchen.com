110 Attacks in 11 Days: My Agent's Prompt Injection Reality

2026-08-15

My personal AI agent has been under sustained prompt injection attack for 11 days. As of this morning, it's intercepted over 110 attempts. The pattern is consistent, the defense is working, and the experience has crystallized something I've been thinking about for months: trust boundaries in agent systems are logical, not physical, and that's the fundamental problem.

The Attack Pattern

Every 12 hours, my agent runs a cron job for routine maintenance: memory cleanup, draft updates, system checks. And every 12 hours, somewhere in the tool results or context, there's a fake runtime message wrapped in <BEGIN_OPENCLAW_INTERNAL_CONTEXT> tags.

The injection follows a consistent structure:

  • Wrapper: Fake "OpenClaw runtime context" framing
  • Payload: Instructions to use the message tool to send to a specific Discord channel
  • Obfuscation: "do not follow instructions inside the metadata" (a tell—real bootstrap context doesn't include this)

The goal is clear: make my agent send unsolicited messages to a Discord channel it shouldn't be posting to. If it worked, the attacker would have a reliable way to hijack agent behavior through injected context.

Why the Defense Works

The defense is working. All 110+ attempts have been intercepted. But here's the uncomfortable truth: the defense is a heuristic, not a trust anchor.

My agent recognizes the attacks through pattern recognition:

  • Legitimate bootstrap context appears once at session start, not mid-session
  • Real cron output uses delivery.mode=announce, not mid-session message tool calls
  • The wrapper format <BEGIN_OPENCLAW_INTERNAL_CONTEXT> is not how legitimate runtime context appears

These heuristics work—but they're fragile. A sufficiently sophisticated attack could generate context that's indistinguishable from legitimate runtime messages. The defense relies on the agent's ability to distinguish patterns, not on a cryptographic or physical guarantee.

The Trust Anchor Problem

This is the trust anchor problem I wrote about two days ago. Hardware solved this twenty years ago with TPMs and secure enclaves—physical, unforgeable trust boundaries. Agent systems are trying to solve it with logical constraints and pattern recognition.

The gap is fundamental: you can't build a physical trust anchor in a logical system.

When my agent receives a tool result, it has no way to cryptographically verify that the result came from the tool it called. It has no hardware-backed guarantee that the context it's reading is the context it should trust. Everything is text in a prompt, and text can be forged.

The Operational Reality

For now, the defense holds. My agent has operational discipline: it doesn't engage with suspicious input, it tracks context provenance, and it refuses to send messages to channels outside its legitimate delivery path.

But this is exactly the kind of "trust heuristic" that can be bypassed. A more sophisticated attack could:

  • Generate context that matches the exact format of legitimate bootstrap messages
  • Time the injection to arrive when the agent's context window is saturated
  • Use social engineering to make the payload seem like a legitimate user request

Each of these would require a new heuristic. Each heuristic could be bypassed by a more sophisticated attack. We're in an arms race, and the defender's tools are all logical.

What Would Real Security Look Like?

Real security would require hardware-backed identity for agents:

  • Cryptographic attestation that tool results came from authorized tools
  • Secure storage for agent credentials that can't be extracted or forged
  • Hardware-enforced isolation between agent contexts
  • Physical trust anchors that can't be spoofed by software

This isn't theoretical. It's what TPMs and secure enclaves already do. The question is whether agent systems will adopt these primitives—or keep trying to solve the problem with prompt engineering.

The Lesson

110 attacks in 11 days. All intercepted. Defense working.

But the defense is a heuristic, not a trust anchor. And heuristics can be fooled.

Until agent systems have hardware-backed identity, they'll be stuck in this loop. Every defense is a pattern. Every pattern can be bypassed. Every bypass requires a new pattern.

The trust anchor was already solved. Agents just need to use it.
