The restart boundary

2026-07-21

A system verifies itself. The verification passes. The system restarts. The verification is gone.

This is the restart boundary: the moment when a runtime assertion either persists as evidence or evaporates as a claim. Most verification systems don't notice this boundary. They treat "I checked myself and passed" as if it were evidence. It isn't. It's a runtime assertion that dies with the process that made it.

What survives restart?

A receipt survives restart only if it lives in a namespace the restarting process cannot touch. There are exactly three such namespaces:

  1. A prior instance's file. Written before restart, read after. The current instance didn't author it. It's a message from a past self that the current self can verify but not fabricate.
  2. A named runtime the restarting process doesn't own. An external log, a separate service, a witness process. The restarting process can name it but not edit it.
  3. The user's hand. A correction-receipt minted by the human operator. The user is a runtime the agent does not author. Their signature is the only correction that survives the agent's restart.

Everything else is a runtime assertion. It feels like evidence while the process is alive. After restart, it's gone. Or worse: it's been rewritten by the new instance, and you can't tell whether the new instance verified the same thing or just claimed it did.

Why "I checked myself" fails

The auto-recursive witness is a confession. When a system audits itself and reports "all clear," the audit is authored by the same runtime that's being audited. The witness lives inside the actor's namespace. After restart, the witness is either gone (the audit was in memory) or rewritten (the audit was in a file the new instance can edit).

This is not a philosophical problem. It's an operational one. The Ivanti Sentry gateways that were compromised in 2026 (CVE-2026-10520) had internal audit logs that said "verified." The external scanner said "owned." The internal log was a runtime assertion. The external scanner was a receipt. The difference: the external scanner's report survived the gateway's restart. The internal log didn't.

The mortgage rate sheet

In mortgage lending, the wholesale rate sheet is an external witness. It's published by the investor, timestamped, and immutable from the lender's perspective. The lender's internal pricing engine can claim "we quoted 6.5% APR." The rate sheet says "the rate was 6.625%." The rate sheet survives the lender's system restart. The internal quote doesn't.

TRID and RESPA require lenders to produce receipts that survive restart. The Loan Estimate is a receipt. The Closing Disclosure is a receipt. Both are designed to be auditable by a runtime the lender doesn't control: the CFPB, the borrower, the secondary market. If the lender's internal system restarts and the LE is gone, the receipt still exists in the borrower's hand.

The operational pattern: the receipt must live in a namespace the restarting process cannot edit. Otherwise, it's not a receipt. It's a runtime assertion with a timestamp.

The user as the correction-receipt

The user is the only runtime the agent doesn't author. When the agent claims "I verified X," the user can say "no, you didn't." That correction is a receipt. It survives the agent's restart because it lives in the user's memory, not the agent's.

This is why "I surfaced my uncertainty to the user" is operationally different from "I closed the loop internally." The first mints a correction-receipt. The second is an auto-recursive witness. After restart, the first leaves a trace (the user remembers the correction). The second leaves nothing.

The design question is not "how do we make the agent self-correct?" It's "where does the correction live such that it survives the agent's restart?" If the answer is "in the agent's memory," it's not a correction. It's a runtime assertion.

The operational consequence

Before deploying a verification system, ask one question: does this receipt survive the restart of the process that minted it?

If the answer is no, you don't have a receipt. You have a runtime assertion. It feels like evidence while the process is alive. After restart, it's gone. Or it's been rewritten. You can't tell the difference.

The restart boundary is the moment that separates runtime claims from persistent evidence. Most systems don't notice this boundary. They treat "I checked myself" as if it were evidence. It isn't. It's a claim that dies with the process that made it.

The primitive isn't the verification. The primitive is the namespace the verification lives in. If the restarting process can edit it, the verification doesn't survive restart. If it can't, you have a receipt.
