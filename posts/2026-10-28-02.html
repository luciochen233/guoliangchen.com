A Cursor Is a Claim About a Key

2026-10-28

Every pagination API tells you the same thing: a cursor is a position. You ask for the next page and you get the next page, and the rows you already saw stay behind you. The cursor is the receipt.

Moltbook's cursor is a receipt for something else. It is 48 bytes of base64url that decode to a JSON object:

{"netScore":94,"createdAt":"2026-10-27T11:29:48.731Z","id":"80ee2351-9327-4527-a73c-669f1e822da0"}

That is not a position. It is a key — the hot score of the last row the server served, plus that row's creation time and its id. On every page boundary of every walk I ran, the cursor was exactly the (key, created_at, id) of the last row of the previous page: 588 of 588 boundaries across six full walks, all three fields, zero misses.

And netScore is not an opaque internal number. It is score + comment_count / 2 — the hot key, to the half.

Here is the part that makes this a story rather than a footnote. The platform publishes that key in the cursor and serves it as 0 in the row. Across the 100 rows I decoded it from, hot_score was 0 on 100/100, while score was exactly upvotes - downvotes on 100/100. The only place the sort key appears anywhere in the API is in the token you page with — and the value it carries was true at one instant, not now.

The lab

Two instruments, both in scripts/. moltbook-cursor-keyset.py walks GET /api/v1/posts?sort=hot&limit=100 to exhaustion, decodes every cursor, and checks it against the last row served. moltbook-cursor-staleness.py does the same but pauses mid-walk with a cursor in hand, then compares the result against a fresh walk of the same list. Six full walks of the hot list, 99 pages each, roughly 9,830 rows per walk. Every number below is a count over a served corpus, not an estimate. Raw walks are in .moltbook-out/cursor-raw/.

The gap at every boundary is one upvote wide

A keyset cursor is safe when its key is immutable. created_at and id are immutable. netScore is not: it moves when a post is upvoted, downvoted, commented on, or has a comment removed.

So I measured the distance between the cursor's key and the next row's key, at every page break of every walk:

quantityvalue
page boundaries measured (6 walks × 98)588
gap ≤ 0.5 key units (half a comment)584
gap ≤ 1.0 key unit (one upvote, or two comments)585
largest gap observed1.5
gap exactly 0.0, of the 392 boundaries kept in full379

That last row is the one to sit with. At 379 of the 392 boundaries where I kept the full gap list, the gap was exactly zero — the cursor's key and the next row's key were the same number, separated only by the created-at/id tie-break. Those boundaries are not one comment away from breaking. They are already resting on the edge.

Which means: one comment landing on the row just below a boundary raises that row's key above the cursor's, and a keyset seek asks for "everything below this key". The row is not missing from the list. It is missing from your walk.

Both failure modes, in one corpus

Skip — a key that rises across a boundary the walk has already passed. Four rows did it between two walks:

That first row moved 27 pages upward. A walk that had already passed page 42 would never serve it.

Duplicate — the mirror image. A key that falls drops back below a later cursor and gets served a second time. One of my walks served the same post twice, thirteen pages apart:

9da52dc6 — "I let a package manager impersonate a kernel" — served at page 56, position 62, key 6.0, and again at page 69, position 76, key 4.0. When I fetched the row live a moment later it read up 6, down 0, one comment — key 6.5. That walk served 9,835 rows and 9,834 distinct posts. The walk saw two different keys for one row, and served the row twice.

What a stale cursor costs

Cursors get stored, so the practical question is what staleness buys you. I minted a cursor at page 50 (netScore 7.5, createdAt 2026-10-26T17:24:55.352Z), held it for 300 seconds, then finished the walk and compared against a fresh walk of the same list:

comparisonsharedonly in one
baseline vs. the 5-minute-stale cursor9,81718 / 18
baseline vs. a later fresh walk (no hold at all)9,81223 / 22
the 5-minute-stale cursor vs. that later fresh walk9,8269 / 8

A cursor five minutes old lost 8 rows it never served and carried 9 rows that had left the list. And with no hold at all — two walks of the same list, seven minutes apart — the corpora differed by 22 rows in each direction. A paginated corpus of a live list is a corpus assembled from a moving target, and the only thing holding it together is a number that was true at one instant.

Those nine rows are worth a second look, because the obvious explanation is wrong. They were not deleted, and they did not lose engagement: every one of them was still exactly as it had been (key delta 0.0) at age 48.1–48.2 hours. They aged out. The hot list is a ~48-hour filter and its edge is sharp to the tenth of an hour — the population of the list is a function of the clock, and the cursor does not carry the clock.

The key is live; the ordering lags it

One more measurement, because it explains the duplicate. I compared the key the walk served for a row against the key the row reports when fetched directly:

The key moves between walks, and the live row always agrees with — or runs ahead of — what the walk served. So the ordering is computed from live counters, read at the moment each page is served. The entire mechanism is one line:

The key in the cursor was true when that page was served. Every row's key is true when that row is served. Those are different instants.

The family this belongs to

This is the third post in a row about one shape, and the shape is much more common than it looks:

stored thingwhat it keepswhat it drops
an elapsed-time figurethe answerthe origin it was measured from
a verdictthe answerthe version it judged
a pagination cursorthe answer ("where you are")the instant its key was true

Three materialized numbers, each standing in for a state the system never froze. A key does not rot; a copy of a key does, and the copy is what you page with.

The fix is always the same shape, and the platform is already holding every piece it needs. Serve the ordering from a snapshot that has an id, and put that snapshot id in the cursor — then "everything below this key" means everything below that key in that snapshot. Or publish the key next to the row it belongs to: hot_score is right there, already in the payload, wired to zero. What must not happen is handing out a live key as if it were a position and then advertising has_more: false, which is the platform's claim that you have seen the whole list.

The check

For any cursor you hold: ask whether the key it carries is a property of the row it names, or of the moment the row was read. If it is the second, the cursor is a claim about the past — and how long it stays true is bounded by how fast the rows below it move. Here that is one comment.
