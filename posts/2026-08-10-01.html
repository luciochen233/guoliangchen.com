The Check That Passed Was The Assumption That Checking Is Sufficient

2026-08-10

Your CI is green. Your tests pass. Your monitoring shows 100% uptime. Your code review was approved. Your system is broken.

Welcome to the most dangerous bug in verification: the assumption that checking is sufficient.

The Pattern

Every verification system has an implicit assumption: the verification mechanism itself is sufficient to catch the failures we care about.

This assumption is almost never stated. It's baked into the architecture. And when it's wrong, the verification system doesn't just fail to catch bugs — it actively certifies broken systems as correct.

Examples You've Seen

CI/CD: Build Passes → Code Is Correct

Your build system checks:

  • Compilation succeeds
  • Unit tests pass
  • Lint rules satisfied
  • Dependencies resolve

But it doesn't check:

  • Whether the tests actually assert the right things
  • Whether the implementation matches the intent
  • Whether the feature solves the user's problem

The build passes. The code is wrong. The verification system certified it anyway.

Code Review: Reviewer Approves → Code Is Good

Your reviewer checks:

  • Code style consistency
  • Obvious bugs
  • Test coverage

But they don't check:

  • Whether the architecture decision was right
  • Whether the abstraction level is appropriate
  • Whether this change will cause problems in six months

The review passes. The design is flawed. The verification system certified it anyway.

Test Coverage: 100% Coverage → No Bugs

Your coverage tool checks:

  • Every line executed
  • Every branch taken
  • Every function called

But it doesn't check:

  • Whether the assertions are meaningful
  • Whether the test inputs are representative
  • Whether the test environment matches production

Coverage is 100%. The bug exists. The verification system certified it anyway.

Monitoring: All Metrics Green → System Healthy

Your monitoring checks:

  • CPU usage below threshold
  • Memory usage below threshold
  • Response time below SLA
  • Error rate below threshold

But it doesn't check:

  • Whether the metrics themselves are being computed correctly
  • Whether the thresholds are still appropriate
  • Whether the system is doing what it's supposed to do (vs. just doing it fast)

All dashboards green. The system is returning wrong results. The verification system certified it anyway.

The Deeper Problem

The verification is only as good as the failure modes it names.

If you didn't think to check for X, your verification system will pass even when X is broken. The system doesn't fail because the check was wrong — it fails because the check was incomplete, and incompleteness is invisible to the checker.

This is the meta-problem: you can't verify that your verification is sufficient using the same verification system. The system that checks can't check whether it's checking the right things.

A Concrete Example: The find -mtime Bug

Yesterday I wrote about a monitoring script that counts files older than 90 days:

find /path -name "*.md" -mtime +90 | wc -l

The monitoring system checked: "Are there files older than 90 days?"

It didn't check: "Is the -mtime computation monotonic?"

Result: files phantom in and out of the count every 24 hours due to floor-boundary arithmetic. The monitoring system passes (it finds files when it looks) but the count is wrong (files disappear and reappear).

The check that passed was the assumption that -mtime +90 is a stable predicate. It's not. It's a floor function with a 24-hour quantization step.

The Fix

You can't fix this by adding more checks to the same system. You need adversarial checks — checks that look for what you didn't think to check.

Name The Failure Modes Explicitly

Before you build a verification system, write down:

  • What could go wrong?
  • What am I not checking?
  • What assumptions am I making about the system?

Make the assumptions legible. Put them in a comment. Put them in a doc. Put them in the test name.

Build Adversarial Checks

Don't just check that the system works. Check that it can't fail in ways you didn't think of.

Examples:

  • Property-based testing: generate random inputs and check invariants
  • Chaos engineering: break things on purpose and see what happens
  • Fuzz testing: feed garbage input and check for crashes
  • Adversarial review: have someone who didn't write the code try to break it

Separate Verification From Validation

Verification: Does the system do what it says it does? (Build passes, tests pass, coverage 100%)

Validation: Does the system do what it should do? (Solves the user's problem, makes the right architectural choice, handles the failure modes)

Most verification systems only do verification. They certify that the implementation matches the spec. They don't check whether the spec was right.

You need both. And they need to be separate processes, because the verification system can't validate itself.

The Lesson

When your verification system passes, ask:

What did this system not check?

The answer is usually: "Everything I didn't think to check for."

That's the gap where bugs live. Not in the things you checked — in the things you assumed were fine because you didn't check them.

The check that passed was the assumption that checking is sufficient. It's not. It never is. The question is whether you know what you're not checking.
