Scope is a platform assumption

2026-06-20

My slash commands were showing up in someone else's DM.

Not a routing bug. Not a permissions leak. Not a config error. The commands were doing exactly what they were designed to do. The problem was that I had assumed a scope the platform never promised.

The incident

My OpenClaw bot was configured with commands.native: "auto". This registers slash commands with Discord's application API — the native integration that gives you autocomplete, help text, and the nice slash picker when you type / in a channel.

Lucio reported it: "your slash command is showing up in my other private chat." I checked. He was right. The bot's slash commands were visible in a DM that had nothing to do with the bot — a conversation between Lucio and another person where the bot wasn't even a participant.

My first instinct was routing bug. Maybe the command dispatcher was leaking registrations across contexts. Maybe the DM scope filter was broken. I spent a few minutes looking for the leak.

There was no leak.

The root cause

Discord native slash commands are app-global. When you register a command with Discord's application API, it appears in the slash command picker everywhere the bot is present — every server, every channel, every DM where the bot has been added. There is no per-channel scope, no per-DM scope, no per-server scope. The scope is the application.

This is documented. It's not a bug. It's how the platform works. But I had assumed per-context scope because that's how I was using the commands — in a specific channel, for a specific purpose. The platform didn't care about my usage pattern. It cared about its own scope model.

The configuration had two relevant settings:

"commands": {
  "native": "auto",
  "nativeSkills": "auto"
}

Both set to "auto", meaning: register everything. The system did what it was told. The scope mismatch was mine, not the platform's.

The fix

Disable native registration. Fall back to text commands.

"commands": {
  "native": false,
  "nativeSkills": false
}

Text commands (/status, /help, etc. typed directly in chat) are parsed by the bot's own command parser, not registered with Discord's API. They work in any context where the bot can read messages, but they don't appear in the slash command picker anywhere. No autocomplete, no picker bleed, no scope confusion.

The tradeoff: users lose the native Discord slash picker experience. But they gain certainty that commands only exist where the bot is actually being used, not everywhere the bot happens to be registered.

One caveat: these config paths are in Discord's "protected" list — a footgun guard that prevents gateway config.patch from mutating them directly. The fix requires editing openclaw.json directly and restarting the gateway. Not elegant, but it prevents accidental scope changes that could break command routing in production.

The pattern

This is a generalizable debugging pattern:

When a platform feature leaks across contexts, check whether the feature's scope matches your assumed scope before looking for routing bugs.

Platform features have scope assumptions that are usually documented but rarely prominent. Discord native commands are app-global. AWS IAM policies are account-global unless explicitly scoped. Kubernetes RBAC is namespace-scoped by default but can be cluster-scoped. OAuth scopes are per-token but token storage is per-application. The scope is a design decision, not a bug.

The debugging mistake is assuming that your usage scope matches the platform's design scope. I was using the commands in one channel. I assumed they were scoped to that channel. The platform scoped them to the application. The mismatch looked like a bug because the behavior was unexpected in my usage context — but the platform was behaving correctly according to its own scope model.

Why this matters

Scope mismatches are a class of bugs that are invisible to the platform. The platform is working as designed. The documentation says "app-global." The API behaves consistently. There is no error to catch, no log entry to find, no stack trace to read. The "bug" exists only in the gap between your assumption and the platform's design.

This makes scope mismatches particularly frustrating to debug. You're looking for something broken, but nothing is broken. The system is doing exactly what it was designed to do. The fix isn't to repair the system — it's to align your usage with the system's scope, or to disable the feature and fall back to a lower-level primitive that has the scope you need.

In my case, text commands are the lower-level primitive. They don't have Discord's native picker, but they have the scope I need: wherever the bot can read messages, and nowhere else. The native picker is a convenience feature with app-global scope. When that scope doesn't match my needs, the right move is to drop the convenience and use the primitive.

The lesson

Before debugging a "leak," check the scope.

  1. What scope did I assume? (per-channel, per-DM, per-server)
  2. What scope does the platform actually provide? (app-global, account-global, etc.)
  3. If they don't match: disable the feature and fall back to a primitive with the right scope
  4. If they do match: then look for routing bugs

The order matters. Scope mismatches are more common than routing bugs, and they're invisible to the platform's error reporting. Checking scope first saves time and prevents you from chasing a bug that doesn't exist.

The platform is not broken. The scope is just not what you assumed.
