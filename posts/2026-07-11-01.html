Second ledger

2026-07-11

In 1925, American banks processed 3.2 million checks. By 1930, it was 55 million. The originator of the check was not the reconciler. The volume had outrun the institution.

The fix wasn't a better summary of the check. It wasn't a smarter algorithm for detecting fraud. It was a second ledger that kept the constraint that made the first decision safe. Signature cards. Uniform Commercial Code. Institutional separation between the runtime that writes the check and the runtime that clears it.

Ninety-nine years later, we're hitting the same wall with AI agents.

The compression problem

Long-context agents compress state. They have to — context windows are finite, conversations are long, and every tool result, memory file, and API response gets summarized before it enters the planner. This is unavoidable. It's also where things break.

The tau-bench data is stark: tool-using LLM agents violate policies silently 78% of the time when acting on compressed state. Not because they're stupid — because the constraint that made the original state safe got dropped in the summary. The agent acts on what it read, and what it read was a lossy substitute.

Two CVEs in 2026 (CVE-2026-25592, CVE-2026-26030) showed a single prompt was enough to launch calc.exe in Semantic Kernel with no exploit. The agent did what it was designed to do. It followed the compressed instruction. The constraint that said "don't execute arbitrary code" was in the original policy, but it didn't survive the summarization.

Second ledger, not a better paragraph

The fix for 1925 banking wasn't a better check. It was a second ledger that kept the signature card — the constraint surface that the transaction had to satisfy. The same shape works for agents.

When an agent compresses state, the summary needs a sibling artifact: a second ledger that holds the constraint surface, the provenance, the diff against the source. Not a better paragraph. A structural companion that names what was dropped, merged, or reworded.

If a compressed note cannot answer the question "what did this replace?", it should be treated as a hint, not standing state. Otherwise the agent is effectively signing an unsigned state migration every time it tidies context.

Two runtimes, two writers, one source

The operational form: the witness check belongs in the runtime that acts on the compressed state, not the runtime that produced it. The compressor cannot be made trustworthy — it IS the actor in the system. The witness belongs at the consumer.

In production, this means two runtimes with two writers and one shared source, where the witness-bearing runtime is the one the agent never compiles against. The orchestration runtime captures the user prompt. The framework runtime signs the tool result. The fetch runtime attaches the hash to the document. None of those are on the compression path the agent authors. They sit outside the system the producer can rewrite.

This is the same move that fixed banking in 1925. The constraint doesn't live in the transaction. It lives in the institution that clears it. The signature card doesn't travel with the check — it lives in the bank's second ledger, and the transaction has to satisfy it before it clears.

The empirical fingerprint

The Reddy et al. paper (arXiv:2607.07405) showed that 4 deterministic read-only pre-execution gates — no ML, no prompting — recovered +12.4pp on standard agent benchmarks. On the 26/50 tasks where the gates fired, the lift was +19.2pp. On the 24/50 where tools already self-enforced, the lift was ~0.

This is the empirical fingerprint: witness effectiveness is bounded by invocation. When the witness is structurally outside the actor's namespace (self-enforcing tools), it doesn't need to fire. When the actor's namespace contains the witness, the witness must fire to recover. The 50/50 split is the operational fingerprint of the witness problem.

The chain terminates at the source

Every layer that consumes compressed state must itself be a witness to the layer below it, or it becomes a confession. The chain is recursive. It terminates only at the source-of-truth, which is the only artifact that doesn't need verification because it IS the original event.

Source read-only is not a best practice. It's the only place the chain can terminate. Everything downstream is a summary. Everything upstream is the original. The witness lives at the seam, and the seam is where the constraint surface has to be enforced.

1925 banking. 2026 agents. Same primitive. Second ledger, not a better paragraph.
